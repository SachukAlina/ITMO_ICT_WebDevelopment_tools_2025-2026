# Лабораторная работа №3

## Цель

Упаковать BookCrossing API, PostgreSQL и парсер в контейнеры, организовать
вызов парсера по HTTP, а затем добавить фоновую обработку через Celery и Redis.
Выполнены все три подзадачи, соответствующие полной версии работы.

## Архитектура

```text
                                   ┌──────────────┐
                      HTTP         │ parser       │──┐
клиент ── JWT ──> API ───────────> │ FastAPI      │  │
                   │               └──────────────┘  │
                   │                                 ├──> Books to Scrape
                   │ очередь       ┌──────────────┐  │
                   └──> Redis ───> │ Celery worker│──┘
                                   └──────┬───────┘
                                          │
                                    PostgreSQL
```

| Сервис | Назначение | Порт хоста |
|---|---|---:|
| `api` | приложение ЛР1, JWT и маршруты интеграции | 8000 |
| `parser` | отдельный FastAPI-сервис синхронного парсинга | 8001 |
| `worker` | выполнение фоновых Celery-задач | — |
| `redis` | брокер задач и хранилище результатов | — |
| `db` | PostgreSQL с данными BookCrossing | — |

Сервисы описаны в
[`docker-compose.yml`](https://github.com/SachukAlina/ITMO_ICT_WebDevelopment_tools_2025-2026/blob/main/students/k3339/Sachuk_Alina/Lr3/docker-compose.yml).
Для PostgreSQL, Redis, API и parser-service заданы healthcheck. API начинает
работу только после готовности зависимостей и автоматически применяет миграции
Alembic.

## Подзадача 1. Контейнеризация

Созданы два образа:

- `api.Dockerfile` устанавливает зависимости ЛР1 и шлюза ЛР3, копирует
  FastAPI-приложение и миграции;
- `parser.Dockerfile` устанавливает парсер ЛР2, parser-service и worker.

Контейнер worker использует образ парсера, но переопределяет команду запуска на
Celery. Все Python-сервисы запускаются от непривилегированного пользователя с
UID `10001`. Данные PostgreSQL и Redis сохраняются в именованных томах.

## Подзадача 2. Вызов по HTTP

`POST /parser/parse` основного API принимает URL, вызывает `POST /parse`
контейнера `parser`, дожидается результата и возвращает клиенту данные книги.
Парсер повторно использует `parse_book_html()` и `save_book()` из ЛР2, поэтому
результат сохраняется в таблице `books` PostgreSQL с upsert по `source_url`.

Перед запросом URL проверяется. Разрешены только HTTPS-страницы отдельных книг
на `books.toscrape.com`; внешние домены, HTTP и страницы категорий отклоняются.
Это ограничивает возможность SSRF через пользовательский URL.

## Подзадача 3. Celery и Redis

`POST /parser/tasks` отправляет задачу `parse_book` в Redis и немедленно
возвращает `task_id`. Worker загружает страницу, разбирает и сохраняет книгу,
после чего помещает результат в Redis. Клиент получает состояние через
`GET /parser/tasks/{task_id}`.

Redis DB `0` используется как брокер, DB `1` — как result backend. Результаты
хранятся один час. Для сетевых ошибок настроены до трёх повторов с backoff и
jitter. Worker ограничен двумя процессами, чего достаточно для учебного стенда
и что не перегружает Docker Desktop.

Если parser-service, очередь или хранилище результатов недоступны, шлюз
возвращает `503 Service Unavailable`, а не внутреннюю ошибку без пояснения.

## Маршруты

Маршруты шлюза защищены JWT из ЛР1.

| Метод и путь | Результат |
|---|---|
| `POST /parser/parse` | синхронно разобранная и сохранённая книга |
| `POST /parser/tasks` | `202 Accepted`, идентификатор задачи |
| `GET /parser/tasks/{task_id}` | состояние, результат или текст ошибки |
| `POST /parse` на порту 8001 | внутренний HTTP-интерфейс parser-service |

Пример постановки задачи:

```json
{
  "url": "https://books.toscrape.com/catalogue/a-light-in-the-attic_1000/index.html"
}
```

## Запуск

Из каталога `Lr3`:

```bash
docker compose up --build -d
docker compose ps
```

Документация основного API доступна по адресу
`http://localhost:8000/docs`, parser-service — `http://localhost:8001/docs`.

Для наблюдения за фоновой обработкой:

```bash
docker compose logs -f worker
```

Остановка с сохранением данных выполняется командой `docker compose down`, а
удаление учебных томов — `docker compose down -v`.

## Вывод

В результате монолитное приложение дополнено отдельным parser-service и двумя
способами запуска парсинга. Прямой маршрут подходит, когда клиенту нужен ответ
сразу. Очередь освобождает HTTP-запрос от длительной работы, позволяет повторять
сетевые сбои и независимо масштабировать worker.
